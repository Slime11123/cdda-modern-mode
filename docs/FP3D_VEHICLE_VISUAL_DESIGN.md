## 1. 结论

- **唯一权威仍是 CDDA 原版 vehicle/map 行为**：移动回合、部件、地图格子、碰撞、伤害、乘坐/驾驶、存档和原版 2D 显示均不改变。
- **增加独立的 3D 车辆快照与车辆渲染器**：先根据 vehicle 的本地 `mount` 部件结构构造刚性局部网格，绘制时只对整车施加位置与角度变换。**不要使用 `vehicle_part::precalc[0]` 计算每一个 3D 顶点位置**。
- 3D 中一辆车是一组属于同一根节点（root transform）的 3D 部件；受损、门开合等仅改变对应部件，不在转向时重新排列车体。
- 第一版采用**程序化模块车辆（车架/底盘/车体外壳/车窗/门/轮/座椅）**，可选为已知车辆原型加载更精细的外观覆盖。**所有车辆表面贴图和美术风格以当前玩家选中的 CDDA 图块包为唯一首选来源，随图块包切换同步刷新**，具体资源解析及缺失处理按第 19 节执行。不要给所有车套同一个轿车模型，因为 CDDA 支持玩家任意装配的车辆。
- 视觉插值只修饰相机和车体姿态，**不回写原版车速、时间、朝向、碰撞或玩家位置**。

## 2. 核实过的源码接入点（以本机当下代码为准）

| 现有位置 | 确认事实与建议 |
| --- | --- |
| `src/vehicle.h` | `vehicle_part::mount` 是车体自身的前后/左右轴；正 X 向前、正 Y 向右；车辆有 `face`、`move`、`turn_dir`、`pivot_anchor`、`pivot_rotation` 和 `precalc`。 |
| `src/vehicle.cpp` | `coord_translate()` / `precalc_mounts()` 将 mount 旋转后映射至地图格；`mount_to_tripoint_abs()` 能获取格子中的部件位置；`pos_abs()` 给出车辆基点绝对坐标。 |
| `src/cata_tiles.cpp::draw_vpart()` | 原版 2D 通过 `here.veh_at(p)` 和 `get_display_of_tile()` 取格子上的代表部件，再绘制 `vp_*` 图块；这是逐格表象，不适合生成整车 3D 网格。 |
| `src/vehicle_display.cpp::get_display_of_tile()` | 已有开门、损坏、变体、颜色等显示规则，可复用**状态语义**，不可复用 2D 逐格布置。 |
| `src/fp3d_snapshot.h/.cpp` | 当前快照有地形 `cells`、人物/怪物/物品 `sprites` 和远景，**没有 vehicles**。可新增只读、拥有自身数据的车辆记录；不得在 GL 绘制时访问 map/vehicle 裸指针。 |
| `src/fp3d_scene.cpp` | OpenGL 单独画地形区块、精灵与建筑玻璃；车辆应作为独立动态对象绘制，不混进静态 8 格地形区块缓存。 |
| `src/fp3d_camera.h` | `floor_height=3.0f`、`eye_height=1.6f`；当前场景的水平地图格跨度约为 1 个渲染单位，车辆也按此比例。 |
| `src/fp3d_input.cpp` | 已存在车辆控制情境识别，3D 驾驶/交互可在现有输入路径上扩展，不另写独立车辆物理。 |
| `tests/fp3d_*_test.cpp` | 已有快照、相机、材质、输入和 GL 测试，可扩展车辆专项测试。 |

**重要**：原版 `vehicle::face.dir()` 是车头方向，而 `vehicle::move` 是滑行方向，`turn_dir` 是预期下一次转向；视觉不得直接把 `turn_dir` 当作已发生的朝向。位置与旋转应采集**同一游戏线程、同一确认状态**下的 `pos_abs()`、`pivot_rotation[0]` 和 `pivot_anchor[0]`。评估当帧三者与 `face.dir()` 的对应关系并用实机测试固定。

## 3. 车辆空间的正确区分

```text
CDDA 原版逻辑（保持不变）
  vehicle.parts[i].mount    车体局部格坐标，固定不变
  vehicle.pos_abs()         车辆地图基点
  pivot_anchor[0]           原版本次确认姿态的局部旋转基点
  pivot_rotation[0]         原版本次确认姿态的旋转角度
  └─ precalc[0] / map.veh_at ... 只做游戏格子占用、交互和碰撞

3D 表现（新增）
  本地网格顶点 + 本地部件挂点（按 mount 生成一次并缓存）
  └─ 统一的 root：世界基点 + 与 pivot 一致的旋转
     └─ 局部车门、轮胎、车窗等状态动画（不改变整车形状）
```

局部车身网格与地图世界坐标关系应统一为：

```text
local = meshVertexInMountSpace - pivotAnchor
world = vehicleAbsoluteGridOrigin + rotate(local, confirmedRotation)
```

其中 `mount` 的 +X 是车头、+Y 是右侧。需要先校准 OpenGL 的世界 X/Z 和 CDDA 地图 X/Y 以及角度正负号，**不能凭直觉在 GL 中直接写 `glRotatef(face.dir())`**。对 0° / 90° / 180° / 270° 和 15° / 45° 加定点对照测试；同一挂点经连续公式落在的世界坐标应与原版 `mount_to_tripoint_abs()` 的**取整误差范围**一致。不能把经过格子取整后的坐标反过来生成车身顶点。

### 原版格子转弯为何在 3D 中会显得变形

原版旋转不是对连续车壳做刚体渲染，而是让各部件的局部 mount 经离散地图格运算重新占位。在斜向时，同一格可叠多件、不同格可出现空隙。俯视 2D 图块容忍这个特点，但第一人称会看到车体裂缝、阶梯边和“移动的车门”。新方案只让逻辑碰撞继续使用这些格；3D 永远按局部模型连续坐标旋转。

## 4. 车辆快照：只读、去重、可见性优先

新增 `src/fp3d_vehicle_snapshot.h/.cpp`（或并入既有 snapshot），例如：

```cpp
struct vehicle_part_view {
    int part_index;           // 仅作本次快照中的部件选择键，不在渲染端解引用
    int mount_x, mount_y;
    std::string type_id;      // 原版零件 ID
    std::string variant;
    bool broken, open, removed, hidden;
    bool seen;                // 原版视野允许显示
    // 分类：frame / wheel / door / window / roof / seat / engine / cargo ...
};
struct vehicle_view {
    int render_key;           // 游戏线程管理的稳定表现 ID；不能用渲染端裸指针
    tripoint_abs_ms origin;
    float angle_degrees;
    int pivot_x, pivot_y;
    int z;
    std::vector<vehicle_part_view> parts;
};
```

- 在 `fp3d_snapshot::capture()` 的当前游戏线程枚举 `here.get_vehicles()`，每辆车采一次，避免对每个格都重复查车；仅采已加载范围。
- 取原版部件 `mount`、类型、显隐、损坏、开关状态及局部层级，不保存 `vehicle*`、`map*` 或零件引用；具体只读接口须遵循 0.I-1 已有实现。
- **不得因为看到车头便泄露墙后整个车厢内部**。按原版玩家可见性判断车体各部分；第一期只画真实可见部分、未见部分不显示。后续如需停放车辆的记忆影像，必须单独按 2D 原版车辆记忆状态复刻，不能读取不可见的实时状态。
- 整车的可见范围、轮廓在跨层和门口需要处理；不能把“地形外立面补绘特例”当作车辆的视野授权。
- 同一快照发布时角度、根位置和部件状态必须一致；车辆删除/分裂/合并、地图切换后失效缓存。

## 5. 车体几何：程序化组装，不直接把 2D 图片直立

程序化模型用 `mount` 的结构格生成 **稳定的车身骨架**，从底往上分层：

1. 车架/底盘：结构部件形成局部平面；相邻车架合并相接面；保留异形车辆、拖车、摩托和玩家扩建布局。
2. 外缘车壳：仅在结构边界生成围板、保险杠、圆角/斜角连接件；不让每个基础格都是一个完全封闭方盒。
3. 轮胎：根据零件 mount 和标志定位在侧方与接地高度；轮胎转向/滚动仅做本地表现，不影响原版动力学。
4. 车门与车窗：按对应部件的实际安装格加门板、铰链和透明窗。门开关按原版状态做瞬间同步或短视觉过渡。
5. 车顶与内饰：车顶不默认透明，座椅、方向盘、货架、车内储物按部件语义布置；玩家坐车内时按视线需要隐藏镜头附近遮挡面。
6. 特殊类型：摩托、巴士、工程车辆、装甲车、船和多节畸形自制车允许不同的 profile/生成规则；不强行套用轿车外壳。

第一版先完成**灰盒形状**（车架、侧板、轮胎、窗）并验证不变形；正式 3D 车辆外观必须通过**当前选中图块包**的 `vp_*` 车辆部件图块解析、匹配变体及破损/开门状态；不得固定使用 UndeadPeople 或外部独立车辆贴图来覆盖其他图块包。现有 `fp3d_materials` 已能共享选中图块包资源，但**车辆图块解析尚未实现**。由于 2D `vp_*` 图块不是现成的完整 3D UV 材质，必须做部件 UV/平面贴花与侧面生成规则；缺少确切图块时先沿原版 `looks_like`/可用同包分类图块降级，仍缺失才使用无贴图中性几何并记录诊断。切换图块包时依照现有材质 revision 使车辆 UV、纹理槽与 GPU 缓存失效并重建，详见第 19 节。

### 可选的整体车型精模

若车型原型与当前结构/关键组件吻合，可以绑定完整外壳模型以得到更真实的轿车或货车；一旦玩家拆掉车架、加长车体或拆车门，自动切换回对应的程序化模块部件。**自制车辆的改装兼容优先于整车模型的完美外观**。

## 6. 车体姿态、动画、驾驶镜头

- **车身永远一体旋转**：同一渲染帧用一组根矩阵变换所有 3D 零件；不按 `precalc[0]` 重排顶点。
- **原版回合仍是权威**：只在确认移动后向表现层发布新姿态。渲染在旧姿态与新姿态间插值（位置 lerp、角度最短弧），允许 15° 转向看起来平滑，但模拟每回合的实际落点不变。正常停在路边不插值，传送、碰撞、解体、读档立即复位。
- **漂移时车头与移动方向可不同**：根旋转跟车头确认方向，位移跟游戏位置；禁止以速度向量强制改车头朝向。
- **车内第一人称**：当玩家坐在原版座位中时，镜头在车体局部坐标系绑定对应座椅，随车体表现根变换平滑移动；眼睛高度相对于原版楼层约 1.6m，可做可配置座椅偏移。交互、命中、逃离车辆使用原版 avatar/vehicle/map 坐标，不让“视觉镜头偏移”控制碰撞。
- 车辆视角转动、驾驶输入仍走原版控制分支；不得用游戏外的自由移动、私设油门物理覆盖原版模拟。

## 7. 绘制顺序与性能

- `fp3d_scene.cpp` 地形不混入车辆，新增 `fp3d_vehicle_renderer.cpp/h`。在建筑不透明几何之后、角色 billboard 与透明层之前绘制**不透明车辆网格**，共用深度测试。
- 车窗等透明面与建筑玻璃统一采用正确的透明排序/深度策略；需要时暂不画车窗半透明，优先确保墙体和车体不穿帮。
- 车辆按独立包围盒做视锥裁剪；只有拓扑、零件装配、损坏到改变外形、材质包切换时重建局部网格。单纯车辆移动/旋转**不能触发地形 chunk 或整车顶点重建**。
- 使用车型/部件材质批次与 VBO 或当前代码可维护的 GL 绘制方式，初期可在现有 compatibility GL 下实现；记录每辆车几何重建数、CPU 构建时间和实际帧成本。
- 视距外可以低模显示在原版允许感知的车辆轮廓范围内，不能因为远景生成而暴露未感知车辆。

## 8. 3D 交互和原版格子“视觉不完全一致”的边界

1. 鼠标准星先选中**渲染几何**，映射到车辆 render_key + 部件索引，在**游戏线程**重新验证仍存在且玩家可合法操作，然后转发原版车辆部件交互；不能因为画面看得到轮胎就绕过距离、视线、权限、行动点。
2. 原版实际碰撞仍按占用格结算。**在斜向转弯、窄门或贴墙行驶时，连续 3D 车壳与逐格碰撞边界可能不完全吻合**：可能出现轻微嵌墙或模型尚未接触即被原版阻挡。这不是模型“变形”，但不可谎称已实现连续物理。
3. 初期通过原版碰撞格调试叠层、外形尽量内收、视觉动画短时收敛、只在合法落点插值来减少穿帮；严禁默默更改原版碰撞/挤压伤害。如果未来需要 100% 一致的连续车体碰撞，应另立车辆物理/游戏规则重做项目。
4. 原版 2D 和 3D 按 F5 切换必须得到同一辆车、同一零件与同一存档状态。Feature OFF 不得编译或访问新 3D 车辆链。

## 9. 分阶段实施及验收门槛

### P1：确认坐标与单辆灰盒车（最先做）
- 固定轿车测试车与单格车架，读取 `mount`、`pos_abs`、`pivot_anchor[0]`、`pivot_rotation[0]`，画本地车架和轮胎。
- 0°/15°/45°/90°/180°/270°、静止/慢速转弯、正反方向、pivot 改变时，各部件相对距离不变；位姿与已确认原版格子状态对照无累积漂移。
- **失败门槛**：任一旋转角度让车体零件之间相对错位、镜像反转或莫名侧跳，则不能进入 P2。

### P2：完整程序化车身与状态
- 补门、窗、车顶、座椅、货箱、轮胎；检测打开/关闭、损坏、拆装、加长、断裂、载具分裂/合并。
- 自制 L 型车辆与摩托/巴士测试，不允许假定所有车都是矩形轿车。
- 同步部件显示与 2D 原版事实，不用虚假的 3D 内饰替代原版部件属性。

### P3：驾驶、乘坐、碰撞与交互
- 车外观察转弯、倒车、原地查看、车内驾驶/换座/下车；物品货舱与修车沿原版操作。
- 验证墙边、窄路、障碍、车祸、翻转/坡道、载具所在楼层，说明每个尚不支持的边界。
- 准星点击零件须在游戏线程做视野、距离、原版操作合法性复核。

### P4：可见性、性能、回归
- 夜间、黑暗房间、墙后车辆、打开窗帘、不同楼层、记忆车辆：不可泄露不可见的车体或零件状态。
- 连续左右转、变速、快速移动、F5 切换 50 次、存取档、换图块包、Feature OFF/ON 。
- 对照无车辆场景记录新增快照 ms、网格生成次数、OpenGL 帧耗时；每帧不因车身旋转重建顶点；未达到项目 FPS 目标时分析后优化。
- 保留 2D 原版与同一存档的动作、车辆部件、损伤、速度、燃油及位置一致性。

## 10. 建议新增文件和修改顺序

1. `src/fp3d_vehicle_snapshot.h/.cpp`：车辆数据复制、可见性、状态。
2. `src/fp3d_vehicle_mesh.h/.cpp`：纯本地车体网格生成，不读地图、不执行业务动作。
3. `src/fp3d_vehicle_renderer.h/.cpp`：3D 资源缓存、统一刚体变换、状态/深度绘制。
4. `src/fp3d_snapshot.h/.cpp`：在现有 `scene_snapshot` 中追加车辆集合，整帧原子发布。
5. `src/fp3d_scene.cpp`、必要时 `src/fp3d_materials.*`：接入动态车、透明层、换包失效、统计。
6. `src/fp3d_camera.*`、`src/fp3d_input.*`、`src/fp3d_interaction.*`：在 P3 阶段才扩展车内视角与准星交互。
7. `src/CMakeLists.txt`、`tests/fp3d_vehicle_*_test.cpp`：ON/OFF 构建、坐标、形状、合法性、性能回归。

**优先级原则**：先证明“转向不变形 + 不改原版规则”，再提升外观真实度，最后才做复杂车辆内饰/交互。任何阶段都不应直接重写 `vehicle_move.cpp` 等原版车辆运动算法来掩盖视觉问题。

## 11. v1.1 强制补充：**全部车辆统一 3D 覆盖**（2026-10-30）

本节是此前 P1–P4 开发计划的**强制验收补充**，不是可选美术优化。若前文对完整车型外壳的描述与本节发生冲突，以「车辆当前真实零件结构优先、不得漏画车辆」为准。

### 11.1 不以“是否为玩家车辆”划分渲染方式

| 来源或情形 | 必须采用统一车辆 3D 管线 | 特别处理 |
| --- | --- | --- |
| 玩家正在驾驶、乘坐或停放的车辆 | 是 | 驾驶镜头、座椅、刚体插值 |
| 城市街道、停车场、车库、道路、野外地图生成的车辆 | 是 | 即使没有驾驶员、发动机损坏或完全不能动 |
| 地图预生成的废弃车、事故车、撞烂的残车 | **是** | 按真实残存零件绘制破损外形，不换回 2D 贴片 |
| NPC 使用、移动中或静止的车辆 | 是 | 复用同一采样/渲染路径；不按控制者做特判 |
| 被碰撞、爆炸、火焰或拆卸改变的车辆 | 是 | 依据部件状态失效对应几何缓存 |
| 玩家自造、改装、加宽、加长、L/T 形及其他异形载具 | 是 | 按安装点构造模块，不假设矩形或四轮布局 |
| 摩托、自行车、巴士、重卡、装甲、工程、船、拖挂等不同类别 | 是 | 使用车型 profile 优化美观，缺 profile 必须有通用模块表现 |
| 分裂出的车体残段、失去车轮/发动机/驾驶位的结构 | 是，只要仍是原版 `vehicle` 对象 | 即使不可驾驶，也绝不能被「可驾驶」过滤条件排除 |
| 车辆已完全解体，仅剩地面零件物品、家具或地形碎片 | **不是 `vehicle`** | 由现有物品/家具/地形渲染职责覆盖，不凭外观生成虚构车辆 |

**统一判定标准**：地图当前加载区域内，经原版合法感知判断需要呈现的任一 `vehicle`，只要还有可表示的真实零件，就必须有 3D 表现；不论来源、是否残破、是否拥有控制者、速度是否为零、是否能启动。**禁止只渲染玩家当前载具；禁止废车或未知车型回退到逐格 2D 车辆图块。**

这里的「全部」指**当前加载且符合原版感知/记忆规则的车辆**，不是将世界中尚未加载、未探索、墙后不可见的全部车提前渲染出来。

### 11.2 与现有本地源码对齐

- `src/map.cpp` 提供 `map::get_vehicles()` 和范围版本，`src/map.h` 声明了两种接口；3D 在当前地图线程经此枚举，不读取存档外的整个世界。
- `src/vehicle.cpp::smash()` 是原版车辆损坏路径之一，源码还存在车辆零件移除、分裂与 `fake_parts` 维护。**不可把“被砸过”“不能动”“总零件少”当作整车不渲染的理由。**
- `src/cata_tiles.cpp::draw_vpart()` 为 2D 从地图格读取展示部件；3D 不得把它或逐格 `get_display_of_tile()` 的结果当成完整 3D 拓扑数据。
- `src/fp3d_snapshot.cpp` 目前只采地形/物品/生物；尚未实现车辆集合。**所有车辆都已正确显示是目标，并非本次代码审查已经实现的功能。**
- 需要核对原版载具临时/虚拟部件（例如 `fake_parts`）的用途：保留其在原版碰撞/视线中的权威行为，但不能无差别把临时占位部件当作独立实体车壳重复建模。

## 12. 全车辆数据流与“绝不静默漏车”机制

### 12.1 同一条管线

```text
原版已加载 map / vehicle 集合
     │
     ├─ 遍历所有 vehicle（包含城市生成车、废车、事故残车）
     │      不是只找“玩家正在控制的 vehicle”
     ├─ 复制每车权威姿态：abs 位置、pivot、确认后的朝向、楼层
     ├─ 复制真实部件：mount、类型、位置层级、安装/损坏/打开状态
     ├─ 对每个部件实施原版视野和记忆过滤（不可泄密）
     │
     ▼
FP3D 独立、只读 vehicle_snapshot[]
     │
     ├─ 模型规则匹配（标准车型精模仅作可选外观增强）
     ├─ 不满足规则 → 程序化车架 + 模块化部件（必选兜底；贴图仍从当前图块包取）
     ├─ 暂缺专用材质 → 当前图块包的同类别或 `looks_like` 图块；全部缺失才用中性无贴图几何并记录原因（不能漏画）
     │
     ▼
统一局部网格缓存 + 单一车辆刚体变换
     │
     ├─ 静态废车：保持固定姿态，省去运动插值
     ├─ 驾驶车辆：仅根姿态平滑插值
     └─ 变损/拆卸：局部或拓扑重建
     │
     ▼
3D 场景深度合成（不叠加逐格 2D 车辆贴片）
```

### 12.2 采集与身份规则

- 车辆集合基于原版 `map::get_vehicles()`，对同一真实车辆做**一次**快照。跨 z 视野、区域重叠和部件占多个格不得生成多辆“复制车”。
- **稳定表现身份**不得直接复用可能被销毁/重用的裸指针地址或单独的部件下标。应在游戏线程维护生命周期映射或快照代际键；加载、卸载、车辆合并/分裂时显式失效。
- 使用原版确认的 `pos_abs()`、`pivot_anchor[0]`、`pivot_rotation[0]`，将 **mount 局部坐标**映射到渲染器。部件可在逻辑地图中离散换格，但不能导致网格局部位置漂移。
- 快照里记录当前可见的**真实零件**与足够的分类信息；同一安装点可能有多层零件（车架、座椅、车顶、装甲等），必须按部件类别分层，不可只复制该格最上方图块。
- 保留源车辆的装配拓扑及局部损伤标志。未参与视觉的引擎/储物/机械属性也不能意外改变原版功能。
- 不可调用会改变零件状态的“显示”辅助代码进行快照；特别要留意本地 `get_display_of_tile()` 在碰到无效 variant 时存在修正零件 variant 的实现。快照必须保持只读。

### 12.3 覆盖统计与告警

调试版本记录以下计数（范围只包括当前加载区域，不包括未感知车辆）：

- `loaded_vehicle_count`：枚举出的不同载具数；
- `eligible_vehicle_count`：通过原版合法感知、应在 3D 呈现的载具数；
- `snapshot_vehicle_count`：采入快照的载具数；
- `renderable_vehicle_count`：至少有一个有效 3D 部件或形状代理的载具数；
- `culled_vehicle_count`：因视锥裁剪或正确遮挡而不产生本帧像素的载具数；
- `unsupported_part_count`、`fallback_part_count`、`empty_vehicle_count`；
- `vehicle_mesh_rebuild_count`、`vehicle_draw_ms`、`vehicle_snapshot_ms`。

不得以「相机外车辆被裁剪」冒充缺失渲染；也不得以「某车辆无专用模型」为由忽略该车。对可见且具有真实结构的车辆，**出现快照遗漏或无法生成任何网格为 P1 阻断错误**，附带车辆标识、部件 ID、坐标与出错原因。

## 13. 废弃、破损和残骸车辆的形状规则

| 原版当前真实状态 | 3D 必须呈现的结果 | 禁止出现 |
| --- | --- | --- |
| 引擎坏了/没油/电池没电，但车体完好 | 外观仍可完整、行为不可驾驶或无法启动 | 根据是否能驾驶决定整车是否显示 |
| 车门打开 | 车门局部开合，留下可见开口；状态源于原版 | 整车消失、车门拖尾、假设原版门自动关 |
| 车门拆掉或部件被真正移除 | 对应门板缺失，车架/内饰按残存结构保留 | 仍用完整轿车外壳盖住缺口 |
| 车窗破损或移除 | 透明材质切换到破碎/缺失的实际形态 | 把所有车窗当作完好的玻璃 |
| 轮胎损坏或缺失 | 损坏时呈现对应破损轮子；移除时轮子消失 | 凭「应有四个轮胎」补画轮胎 |
| 车架、装甲、车顶、保险杠毁坏或拆除 | 按剩余真实结构重构外缘、缺口、局部残片 | 仍强制生成封闭完整车壳 |
| 只剩局部车架/少数零件，但仍是 `vehicle` | 显示残存车架及对应零件，允许不规则低矮残骸 | 因“不是标准车型”而跳过 |
| 玩家后装货箱、发动机、更多车轮、加长车架 | 新增对应的 3D 部件并更新邻接表面 | 模型始终停留在出厂原型 |
| 车辆分裂成多个原版载具 | 各残段独立刚体，分裂后身份和缓存正确更新 | 视觉上强行黏回一整辆车 |
| 原版已销毁整个车辆对象 | 不再渲染该车辆；由掉落物/地形模块呈现剩余东西 | 留下一辆不可交互的“幽灵车” |

**注意状态语义**：原版部件「受损」「损坏/失效」「已移除」不是同一概念；具体阶段阈值须由该零件当前实际字段决定，而非单一 `broken` 布尔值扩展到全部情形。建议映射为：正常 / 轻损 / 重损 / 失效 / 缺失，并通过可用字段、类型与实际效果进行核验。锈蚀、烧焦、凹陷等**不能凭“停在路边”就虚构为真实损坏**；若作为纯装饰只能稳定、可关闭且不会遮蔽真实部件状态。

### 13.1 标准外壳优先级不得吞掉破损

**优先级固定：真实部件状态 > 程序化结构 > 精模装饰。**

- 精模可以是透明/分片的外观覆盖，但必须让车门、玻璃、装甲、车顶和车架缺失真实可见。
- 默认先支持逐模块外壳组合；只有**已验证结构兼容、能局部关闭部件**的完整车型精模才能启用。
- 一旦结构不匹配，应退回对应局部模块或整车程序化网格；不能回退到原版 2D 车砖块，也不能套上错误的标准轿车。
- 对未知 ID、模组新增车辆零件使用标志/位置类别推断能表示的几何。实在无法判断时画可辨识的通用零件占位，并记录该 ID，**不要丢弃整个载具**。
- 相邻模块接面合并、轮廓圆角和共用外壳属于外观修饰；不能跨越真实缺失的车架和开口造出“幻影钢板”。

### 13.2 极端破损、杂乱堆叠与假部件

- 多部件同 `mount` 依据实际安装层级显示；同格的轮胎、底盘、座椅、装甲、车顶不可相互覆盖成无意义方盒。
- 假部件（用于原版行为的临时占位）不默认作为独立可见实体显示；必须验证其与真实零件的关联，不得因重复生成造成“第二套车壳”。
- 无轮车辆可作为静止或移动的原版载具存在；显示位置随原版确认姿态，不凭视觉推断需要轮胎补全。
- 车架很少、不连通或极度异形时，按真实模块集合绘制；若原版实际将其分裂为多个对象，再按分裂后的对象各自绘制。
- 无可显示真实部件的特殊空载具需要诊断与安全忽略（不能死循环/崩溃）；**空载具不应作为允许漏画正常废车的普遍借口**。

## 14. 车辆、残骸与场景对象职责划分

要先按**对象类型**，再按美术外观分类，不能仅凭名称含「wreck / smashed / junk」判断是车辆。

1. **真实 `vehicle` 实例**（包括城市生成和受损残留）：本设计的统一车辆快照 + 3D 网格渲染器负责。
2. **车上物品、乘客、车载货物**：按原版车内物品/乘员语义分别显示。可见的货物要正确附着在车辆局部坐标，不要随地形格刷新而脱离车身；不该看到的货物仍隐藏。
3. **已脱离车辆的零件物品、废钢铁、玻璃碎片**：由 3D 物品渲染模块负责，不能为了“补全废车”把这些地面掉落物凭空拼回一个车体。
4. **某种地形/家具形态的报废车景观或非车辆障碍**：由地形/家具模块负责。若其外观确实需要 3D 废车造型，可单独开发装饰模型，但**不得宣称它拥有原版 vehicle 的驾驶/拆卸能力**。
5. **世界尚未加载的车辆或远景轮廓**：只能在原版已知、允许显示的数据层做低细节占位；不能为了远景城市让未发现的车辆凭空出现。

**验收时两类都检查**：既核对所有可见 `vehicle` 进入车辆渲染器，也检查城市里看起来像废车的场景对象是否由对应地形/家具/物品层合理显示。不能将二者混为“get_vehicles 已覆盖整个废车场景”。

## 15. 可见性、地图加载、渲染距离与缓存约束

- 统一车辆采样必须沿用 `fp3d_snapshot` 当前多层可见性设计，不能因车辆包围盒跨入一个可见格就读取并完整暴露隔墙的车体、车内零件或乘员。
- 静止废车在地图记忆中如何显示需按原版记忆中的**已观察车辆图块**单独设计；不得从不可见的实时 `vehicle.parts` 更新其破损/拆卸状态。仅具备可见实时片段时，可只绘制经合法观察的局部车壳。
- 车辆只在加载区域内枚举；当前多楼层扫描可能把同一车在不同层的可见部分重复遇到，必须按身份去重并保留相应部件高度。
- 3D 原版地形的可见性授权与车辆实体的可见性不是一回事；车辆必须对照原版人物/车辆可见条件。仅通过地形可见格筛选是起点，不足以覆盖车内/遮挡/记忆逻辑。
- 渲染裁剪、LOD 和 GPU 缓存不得制造跨镜头“凭空消失/突然补全”的破损车。允许距离造成精度变化，不允许丢掉车、恢复不存在的门/轮胎。
- **缓存分离**：车体拓扑 key（真实 mount + 零件 ID/装配层）与外观状态 key（损坏、打开、材质 revision）、运动 pose key（位置/角度）、可见性 mask 独立维护。转弯只动 root；局部损坏只使相关 mesh/材质失效；地图 chunk 不应因车辆移动重建。

## 16. 统一覆盖专项验收矩阵（新增硬性关卡）

下列用例需要建立**可复现的真实游戏地图和车辆状态**，并保存 2D 原版 / 3D 对照截图、快照清单、日志。**不能只看标准轿车截图就宣称「所有车辆已支持」。**

| ID | 实际场景 | 必须满足的结果 |
| --- | --- | --- |
| V01 | 玩家完整轿车停放，围绕车走动 | 车体连续、无逐格裂缝；部件位置稳定 |
| V02 | 玩家车辆以 15°、45°、90°、180° 转向、倒车 | 车体保持刚性，pivot 改变不跳件/跳车 |
| V03 | 城市街道地图生成的多辆废弃车 | **每一辆可见且为 vehicle 的废车均有 3D 外观**，与 player ownership 无关 |
| V04 | 城市停车场、车库、路口、野外道路生成的车辆 | 非驾驶状态也会被枚举，不依赖 `player_in_control()` |
| V05 | 车门丢失、门打开、门重装 | 对应门板变化；其余车壳稳定 |
| V06 | 碎窗、窗缺失、车顶坏、保险杠缺失 | 破损位置与原版状态一致，不被完整精模覆盖 |
| V07 | 单侧两轮缺失、完全没轮、发动机已坏 | 能正确显示剩余结构，不以可驾驶性过滤 |
| V08 | 严重破损只剩 1–3 个车架模块 | 仍显示残存网格；不生成虚构完整轿车 |
| V09 | 玩家自制 L/T 形、加长车、超宽车 | 按各 mount 组装，能看到异形轮廓 |
| V10 | 摩托、自行车、巴士、货车、装甲、船等 | 没有专属模型也由通用模块渲染 |
| V11 | 车辆碰撞、砸毁、零件拆卸/重新安装 | 局部 mesh 正确更新，无持久旧几何 |
| V12 | 分裂/合并、拆到只剩残段、载具删除 | 载具数与原版一致，无幽灵车、重复车 |
| V13 | 两辆废车占相邻格/车体重叠视觉区域 | 渲染/身份去重正确，不把两车合为一辆 |
| V14 | 车辆部分在墙后、暗室、楼层边界 | 没有透视泄露、完整车壳跨墙暴露 |
| V15 | 走远后返回、地图卸载/重载、存档读取 | 破损姿态稳定，无缓存错绑 |
| V16 | F5 连续切换 2D↔3D，含驾驶/静止/废车 | 2D 保留原版渲染，3D 始终同一车辆状态 |
| V17 | 切换图块包、找不到特殊载具纹理 | 必须有通用模块/材质，**禁止退回 2D** |
| V18 | 地面零件/家具式废车/已不再是 vehicle 的碎片 | 由其真实类型渲染，不误判为仍可驾驶车辆 |
| V19 | 大街同屏大量停放车，少量在行驶 | 静态网格缓存有效，驱动 pose 不触发重建 |
| V20 | 首尾车辆/局部车壳超出原版载具加载范围边界 | 不越界、不卡死、无未加载车辆信息泄露 |

### 判定规则

**功能强制通过（不得降级）**

- V01–V20 均有自动测试或可复现的人工操作步骤和明确结果；不能以测试尚未覆盖换取「已完成」标签。
- 每一辆**符合原版感知且有真实可显示零件**的 `vehicle` 必须在快照中恰好出现一次，并生成至少一部分合法可见的 3D 几何；不得产生静默遗漏、重复、或以 2D 逐格图块兜底。
- 实际已移除的门、轮胎、车顶或车架不能被通用模型补回；损坏语义不能与「完全缺失」混淆。
- 转向及静止观察时，同一车辆未损坏零件的**局部相对距离保持不变**，根姿态跟随原版确认状态。
- 地图和车辆可见性规则不能被视觉优化绕过；不得泄露未见车体、乘员、货物或隐藏状态。
- 2D 原版存档和运行逻辑、车辆装配、燃油、速度、碰撞/伤害、回合必须不受 3D 绘制影响。

**量化性能（先采基线再设置放行阈值）**

- 在标准城市、密集停放车街道、驾驶场景分别采集空场/带车的 snapshot、mesh build、draw CPU/GPU 数据；记录中位数与高百分位，目标与项目现有 1080p/60 FPS 性能方向保持一致。
- 停放且部件状态不变的废车，在稳定场景中不应每帧重建静态网格；车辆纯位移或转向不应每帧重建顶点。
- 未达到实际性能目标的场景，保留分析与优化任务；**不能以偷偷剔除废车、降低合法感知范围或强行 2D 替换来换 FPS**。

## 17. 与既有 P1–P4 结合的修订开发顺序

为避免「只做出了可驾驶轿车，路边废车全没了」，原先 P1 前新增 **P0-V 车辆覆盖发现关卡**：

1. **P0-V：枚举与场景覆盖**。建立一份包含玩家轿车、城市废车、受损车、自造车、极小残骸的固定测试地图/存档；证明不同来源的 `vehicle` 均被 `map::get_vehicles()` 唯一枚举，区分物品、家具和地形残骸。先能诊断再开始美术。
2. **P1-V：统一灰盒渲染**。对**所有采样的真实车辆**按 mount 生成灰盒，静态废车与玩家车用同一个 mesh builder；通过 V01–V04、V08、V09、V13 的基本姿态与覆盖测试。若街道废车仍只有 2D、任何合法载具无几何，P1 不通过。
3. **P2-V：真实状态和完整通用 fallback**。加门、窗、车架外缘、车顶、轮胎及破损/移除；通过 V05–V12、V17、V18；未匹配零件必须有可辨几何和诊断日志。
4. **P3-V：驾驶、乘坐、交互与动态变化**。按原计划保持原版输入与物理；通过 V02、V11、V12、V16 以及驾驶/乘坐碰撞测试。
5. **P4-V：可见性、性能和全车型回归**。通过 V14、V15、V19、V20，记录 2D/3D 功能一致性与性能测量；逐步美化，不能降低 P0–P3 已通过的覆盖能力。

建议对应代码和用例（新增之前先核对现有构建目标和测试框架）：

- `src/fp3d_vehicle_snapshot.h/.cpp`：全部车辆遍历、状态/可见性、身份去重、统计；
- `src/fp3d_vehicle_mesh.h/.cpp`：包含破损与缺失的通用模块规则；
- `src/fp3d_vehicle_renderer.h/.cpp`：刚体姿态、车体 mesh 缓存和 fallback 材质；
- `src/fp3d_snapshot.h/.cpp`、`src/fp3d_scene.cpp`：集合接入与显示顺序；
- `tests/fp3d_vehicle_snapshot_test.cpp`：地图生成/废车/可见性/多层/去重；
- `tests/fp3d_vehicle_mesh_test.cpp`：多 mount、缺门、缺轮、异形车、极端残骸；
- `tests/fp3d_vehicle_render_test.cpp`：持续转向、换包、F5、缓存重建统计；
- `qa/0i1/vehicle-coverage/`：固定场景说明、期望清单、真实截图/日志（执行验收时再生成）。

## 18. 总交付定义（Definition of Done）

**只有满足下列条件，才能在项目进度中写「3D 车辆系统已完成」：**

1. 城市道路上的废弃车、损坏车、不能开的车，和玩家车一样拥有完整一致的**统一 3D 渲染路径**；没有按控制者、可驾驶性或车型名称硬编码的漏车例外。
2. 实际当前 `vehicle.parts` 决定结构，部件受损、缺失、改装、分裂、删除能正确同步；尤其不会把废车渲染成崭新完整汽车。
3. 所有有真实可表示部件的合法可见车辆均可由程序化生成器绘制；**专属模型和贴图永远不是渲染成功的前提**。
4. 整车转弯/旋转采用刚体变换，不发生原版逐格车砖块式拉扯、伸缩、错位；已知原版离散碰撞边界偏差明确测试并记录。
5. 原版 2D 显示、存档、行为、可见性和功能没有回归；有实测截图/测试/日志证明 V01–V20 的覆盖情况，并如实列出所有未通过项。

**执行纪律**：此文件是实施和验收方案，不代表本次已经完成任何 3D 车辆代码、编译、运行或测试。后续实现必须逐阶段报告真实结果，不能把计划写成已完成事实。

## 19. v1.2 强制补充：车辆 3D 贴图必须来自当前游戏图块包（2026-10-30）

**最终视觉要求**：玩家当前选择什么 CDDA 图块包，3D 里的**所有车辆**（玩家车、NPC 车、街道静置车、废弃/受损车、玩家改装车、特殊载具）都必须以**该图块包的车辆零件图片**为优先纹理来源，保留当前图块包的画风、颜色和像素表现；切换图块包后同一场景的车辆也必须同步更新。不能出现「地形使用不死人图块，汽车却始终使用项目内固定贴图」「更换为 RetroDays 后汽车仍是 UndeadPeople 外观」的情况。

本条只规定**材质来源**；车辆的形状、门窗/轮胎的真实缺失、车体旋转、原版碰撞规则仍以第 1–18 节为准。**2D 车辆图块用于贴在 3D 连续表面，绝不用于逐格移动/变形 3D 车身。**

### 19.2 车辆零件纹理匹配优先级（只读、同包）

车辆快照增加**美术请求数据**，至少包含：部件 `vpart_id`、实际变体 ID、所属安装层、原版确定的正常/打开/损坏状态、方向/连接类型、需要可见的面类型以及纹理选择所需的稳定键。贴图解析器直接从**当前选中 tileset** 查询资源，不能从 3D 层猜测固定磁盘文件名或硬编码某个图块包目录。

对每个车体部件按下列顺序解析：

1. **精确匹配当前图块包的车辆部件**：依照原版 `vp_<vpart_id>` 和对应的变体命名规则查找，并按打开/破损 subtile、正常/破损资源状态获取前景/背景等图片；注意原版还有自定义 tile variant、旋转和连接图块，具体格式必须以 `cata_tiles` 与 `tileset` 的 API 为准。
2. **同包原版车辆零件继承**：若精确 ID 缺少图片，按 `vpart_info::looks_like` 及原版进一步的车辆/furniture fallback 解析。需限制循环深度、防止循环继承，并记录每级命中来源。
3. **同包同类别合理替代**：若上一步仍不存在，使用当前图块包里适合的通用车架、金属、轮子、玻璃等已存在可读图块来表达相近部件，且**仅作美术退化**；不得谎称该图块代表实际零件种类。
4. **彻底缺素材的安全表现**：仍渲染由真实零件生成的 3D 网格，使用清晰的中性无贴图色块/诊断占位并输出缺失 ID。只有这一步允许没有来自当前图块包的纹理，不能擅自加载其他图块包或外部固定车模贴图来代替。

**禁止**：把 `t_floor` 作为所有车门贴图、把整车图块强行拉伸铺满车顶及四面车壳、全部车辆共用一张汽车贴图、因为没有纹理就删掉整辆废车。只要该包提供相应零件图片，渲染必须实际引用该包对应资源；通用颜色兜底不是「已完成贴图适配」。

### 19.3 2D 图片贴到 3D 车辆表面的规则

现有图块包主要提供**2D 精灵，不保证有真实 3D 侧面/法线/PBR**。因此需要一套可重复、稳定的**2D→3D 展示映射规则**，不能期望像游戏原生 3D PBR 材质那样覆盖全部立体面。

| 车辆模块 / 面 | 贴图来源与建议映射 |
| --- | --- |
| 车架、底盘、车壳 | 使用当前图块包对应 `vp_*` 部件图片作为主要可见表面或装饰贴花，侧面采用**同一图块或其颜色/像素信息生成的简化侧板**；不能当作另一款车的纹理 |
| 引擎盖、后备箱、车顶 | 当前部件顶面图块按本地朝向贴图，UV 固定于局部 mount，不因世界转弯重新投影 |
| 车门、车窗 | 对应当前图块包的门/玻璃零件，开门/破损图块与真实开合/缺失状态对齐，窗透明度按像素 alpha 与 3D 透明层处理 |
| 车轮、轮胎 | 使用当前图块包轮胎图块作为两侧平面/侧向贴花，可配合简化轮胎厚度几何；不存在的轮子不能靠贴图补回 |
| 座椅、货架、武器架、车灯、装甲及其他功能件 | 按真实 `vpart_id` 取对应图块，放到局部挂点/合理朝向，未覆盖侧面用同包色调辅助 |
| 破损废车 | **只渲染残存真实零件的纹理与结构**，对应破损变体或原版可读的状态；外观不能套完整无损的车辆皮肤 |
| 图块包中无单独侧面素材的部件 | 沿用当前包图片绘制正面/顶面，侧面用不改变语义的同包颜色简化面，不凭空宣称拥有真实细节 |

- 2D 零件图块的**前景、背景、透明、像素缩放/offset、变体和多 sprite** 要在材质复制时保持合理语义；不得丢掉关键前景后误认为纹理正确。
- 对车辆纹理采用**像素风格友好的采样**（例如与当前图块包一致的最近邻，或由现有设置决定），避免明显模糊与相邻图集纹理串色；为透明边缘留 padding。
- 3D 纹理坐标必须保持**车体局部坐标系**。每次确认转弯只改变根矩阵，不重算部件 UV，也不让贴图像地面投影一样滑过车壳。
- 贴图旋转不能采用原版 2D 逐格取整之后的位置旋转；车体的朝向对齐与**方向性图块纹理**是两个独立概念，须分别校验。
- 可以为不同车体部件赋予几何法线/亮暗以帮助立体观察，但**不可将 3D 光照重新着色成与当前图块包完全不同的材质风格**。

### 19.4 新增专门的车辆图块解析/图集路径

建议在 `fp3d_materials` 增加：

```cpp
// 设计草案：具体类型、命名、原版 sprite/variant 查询需编译对齐。
struct vehicle_texture_request {
    std::string part_id;
    std::string variant;
    bool open = false;
    bool broken = false;
    std::string surface_role; // top / side / wheel / window / interior ...
};
std::string vehicle_key( const vehicle_texture_request &request );
std::optional<uv_rect> lookup_vehicle( const vehicle_texture_request &request );
```

实施须满足：

1. 在 `fp3d_materials::prepare(scene)` 添加 `scene.vehicles` 的**可见车辆素材请求**，包括街道静置废车。按 key 去重，每种部件/状态只占用一次图集资源，不按每辆车重复拷贝相同图片。
2. 解析逻辑独立为 `resolve_vehicle_part(...)`（推荐），以选中的 `tileset` 查询 `vp_*` 和对应 fallback；不要把车辆当成 `terrain_kind`，也不要把零件当成 `sprite_kind::item` 误用贴图。
3. 保留复制纹理到 SDL 目标图集、通过 `SDL_GL_BindTexture` 供 GL 使用的现有资源路线；不要从其他线程直接持有原版 `texture*`、也不要假设 SDL 内部纹理就是可持久保存的 GL ID。
4. 当前共享图集为 **1024×1024 / 64×64 = 256 槽**。城市里车型/变体很多时不能静默丢弃车辆贴图：应先量测实际同时请求数，再评估多页图集、分配独立车辆图集、优先级/LRU 和分批绑定。**不可只在满槽时让后出现的路边废车永远变成紫色棋盘**。
5. 车体网格、部件纹理、材料的缓存分别存放：车辆拓扑变化重建局部几何；破损/开关门更换对应纹理/UV；仅位置和方向改变不重新上传图块图片。
6. 标准车型精模可以决定**几何外形**，但最终车辆纹理仍需由当前图块包提供；禁止精模自带的固定车身材质覆盖用户选中的图块包。
7. 贴图切换采用与地形/人物一致的生命周期：原版图块资源卸载前撤销旧绑定、重载后更新选中 set、`revision` 自增、车辆图集与 UV/GL 缓存失效。**资源变化只影响画面，不改车辆状态/存档**。

### 19.5 图块包切换与用户体验

- 用户在原版设置里切换任何已安装的、可用的图块包，3D 所有车辆立刻使用新贴图包资源（按现有重载流程，在完成资源重建后的首帧或明确加载状态下更新）；不要求重开存档、不要求另行配置「3D 车辆专用贴图包」。
- 初始资源使用当前选中的图块包，不硬编码 UndeadPeople。开发测试重点覆盖当前项目已有的 **UndeadPeople ↔ RetroDays ↔ UndeadPeople** 往返。
- 同一车辆、相同零件、相同游戏状态：换包后**几何、零件缺失、车体朝向、交互、速度均保持不变**；仅贴图/风格随包改变。
- 若新贴图包不存在某车部件的图块，按 19.2 的**同包优先 fallback** 逐级处理；不读取上一图块包的缓存，绝不能“混包”。返回旧图块包后显示对应原风格。
- 不同贴图包可能提供不同数量和方向的车辆图片。不得编造不存在的 3D 侧面图；遇到 2D 素材不足应诚实使用同包派生的简化几何面，并记录素材覆盖率。
