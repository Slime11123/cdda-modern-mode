## 1. 用户最终确认的目标（最高优先级）

用户想要类似《异星工厂》主菜单：**游戏一启动，原本的主菜单背后就能看到独立、持续运行的 CDDA 原版 2D 实机游戏场景**。主菜单的 ASCII 标题、左侧菜单、版本号、底部提示、交互以及子菜单 **全部保留**，**只换背景**。

重要的硬性约束：

1. **不使用玩家自己的世界、存档、角色或当前游戏画面**；不录玩家游戏画面，也不读取/修改玩家存档。演示世界必须彻底隔离。
2. **调用原版 CDDA 生成、渲染与模拟逻辑**：地图/overmap、车辆原型及 vpart、NPC 装备及 AI、僵尸寻路、近战/远程攻击、车辆运动、天气/光照。**禁止重新手工拼接车辆贴图、绘制假的 NPC 武器、制造固定的假战斗动画。**
3. 场景按顺序运行/切换，包括：城市车辆、NPC 近战、NPC 远程射击与僵尸、车辆在道路上行驶。不能每几秒反复播完全一样的动作。
4. **主菜单演示画面不允许出现真正可攻击的玩家角色**：CDDA 内部如果必须有 avatar 满足 game/地图逻辑，只能作为无敌、不可被发现、不可出镜的隐藏 spectator，并要确保其死亡、对话、背包及 UI 不打断演示；不能让 NPC/僵尸追着 spectator 打。
5. **采用原版实时回合模式**驱动演示（例如 `TURN_DURATION`），无人输入时仍能更新；镜头需自主平移/追车/换场景，不能停在原地。
6. 背景必须是当前用户配置的不死人贴图包 **`UNDEAD_PEOPLE_BASE`** 的原生 2D 画面，**清晰、比例正确、不拉伸、不模糊**。优先像素最近邻、原尺寸或整数倍显示，宽屏覆盖时合理裁切；不能变成一堆方块。
7. 正式游戏操作、已有存档、玩家正常 2D/3D 切换以及其他项目模块均保持原样。不要另做临时测试版取代常用启动器。

### 具体当前 worker 代码行为（不是产品保证）

- `scene % 4` 分成 4 类；场景开始根据附近 overmap 查找 `road` 并调用 `g->place_player_overmap(road)` 进入新位置。
- `kind 0/2` 使用原版 `here.add_vehicle(vproto_id("car"), ...)` 生成真实车辆；`kind 1/3` 使用 NPC 模板 `NPC_gun_store_survivor`、`survivor_camper` 与 `g->place_critter_around(mon_zombie,...)`。
- `kind 2` 另尝试 `engine_on = true; velocity = 600; cruise_velocity = 600` 的无人驾驶车辆；**必须实测物理是否真的推进，不能仅凭设了速度就声称已经在驾驶**。
- 每场景目前迭代 78 步，`actor.set_moves(0)` 后运行 `do_turn()`、重绘和 `SDL_Delay(145)`；视角用 `actor.view_offset = tripoint_rel_ms(-9 + step/4, ..., 0)`。
- 仍然存在隐藏的 `avatar` 作为 CDDA 内部必要载体，当前设置 `DEBUG_NODMG` 与 `DEBUG_CLOAK`；需要进一步确认**角色不会出镜/成为怪物攻击目标/触发死亡中断**，否则改为纯 spectator 摄像机或隔离地图摄像中心。
- 场景要保持用户要的**原版实时回合**，而不是外部假动画。子进程更新速度可以依据原版 `TURN_DURATION`，UI 每帧刷新，但注意 `do_turn()` 在遇到强制输入/死亡弹窗时可能阻塞。
- 工作进程通过文件通道发布帧。**这仍是原版真实场景实时模拟 + 画面传输，不是直接共享 SDL render context；需要解决生产/消费时序造成的冻结。**

### 当前高清传输源码注意事项

- `fp3d_menu_native_capture.inc` **最新源码已从旧 BMP/720×405 方案改为 PNG、按真实地形像素比例且上限 1600×1000**，`SDL_SetTextureScaleMode(... SDL_ScaleModeNearest)`。
- `menu_frame_interval = 155` 毫秒（约 6.5 帧/秒）。用户要求连续运动，建议根据性能优化到真实可用的更高帧率，勿因 CPU/磁盘负担直接扩大无上限帧队列。

## 5. 当前用户要求修复（优先顺序）

**P0：隐藏 spectator / 防止演示停摆。**
- 做到屏幕没有玩家形象，但游戏内部保持必要模拟上下文；不得让僵尸追 spectator，也不能因玩家死亡、对话、弹窗或菜单导致 `do_turn()` 停止。
- 必须区分真正的 NPC 对战僵尸和 NPC 围着隐身 avatar 站着不动。使用原版 AI 敌对关系/行为设置，禁止硬画“射击线”模拟。

**P1：原版实时模式 + 连续播放。**
- 在 worker 中让原版游戏逻辑真实前进，独立场景导演选择镜头位置；不能只显示最后一帧。
- 验证连续真实帧的数量与像素差异、UI 无输入时保持刷新，以及主菜单窗口长时间运行不冻结。
- 场景按顺序播放，至少车辆/近战/远程/行驶四类；避免大量一模一样的循环动作。

**P2：独立移动镜头。**
- 观察 `actor.view_offset` 是否实际影响 `g->draw_ter` 的摄像中心；如果只是内部数值变化但画面不动，需要沿用原版 2D 视口偏移/视线机制，并独立于 actor 的位置计算镜头中心。
- 可缓慢平移、追车或切场景；不得移动玩家存档内的角色。

**P3：高清、比例与清晰度。**
- 比对主菜单 2D 原生画面和输出帧：不能把低分辨率 720×405 放大后模糊；核对原始地形 RECT、renderer logical size、窗口尺寸、最近邻参数及裁切坐标。
- 别裁掉大部分道路或让车辆变形；确保贴图包为 `UNDEAD_PEOPLE_BASE`。

**P4：性能、隔离、可靠性。**
- 限制工作进程 CPU/内存和 PNG 文件数量、缓存磁盘体积；停用后终止子进程。
- 避免重入两个 worker、丢帧后的无限等待、路径或 world 创建失败引发普通游戏无法进入；失败要自动降级、可退出。
- 使用独立目录 `runtime\0i1\user\menu-demo-sandbox`，绝不读取/覆盖 `runtime\0i1\user\save` 或玩家世界。

## 13. 2026-11-11 凌晨：帧率根因（PNG 编码）、共享内存直传、公路行驶

用户反馈：① 镜头还是一卡一卡，NPC 卡住时镜头就不动；② 取消玩家视野限制（远处发暗）；③ 开车场景几秒后回到初始状态、人不在驾驶位在后面；④ 要连续的公路行驶。

### 13.1 关键发现：卡顿的根因是 PNG 编码，不是世界模拟

在 worker 里加了分段计时探针（`[PROF]`），实测：

```
[PROF] render=14ms  publish=185ms  turn=2ms     ← 旧版（PNG 写盘）
[PROF] render=11ms  publish=1ms    turn=1ms     ← 现在（共享内存）
```

也就是说：一次 `do_turn()` 只要 2ms，渲染 11–14ms，**PNG 编码+写盘吃掉 140–190ms**。
所以之前无论怎么调帧间隔都卡在 4–5fps；而镜头只在"出新帧"时才动，看起来就是一卡一卡、甚至停住。

### 13.2 改动

- **共享内存帧通道**（`fp3d_menu_native_capture.inc`）
  - worker 渲染完直接把 `SDL_Surface` 像素 memcpy 进命名共享节（`Local\cdda_menu_demo_frame_<pid>`，seqlock 奇偶序号防撕裂），父进程用 `SDL_UpdateTexture` 直接上传，**完全不编码、不落盘**。
  - `frame_shm.txt` 只写一次（节名 + 宽高）；PNG 文件路径保留为回退。
  - 实测：**50 fps** 产出、父进程 43 次/秒重绘；目录里不再产生任何 png。
- **镜头改由墙钟驱动**：主循环拆成"每帧更新相机 + 渲染"与"每 150ms 推进一个世界回合"两部分；相机不再和回合绑定，世界慢也不会冻住画面。
  - 相机位置分整数格（`view_offset`）+ 小数格（`set_native_menu_pan()` 像素平移）。
- **取消视野限制**：演示进程内 `map::apparent_light_at()` 对已加载范围一律返回 `BRIGHT`，`Character::sees()` 两个重载对 avatar 一律返回 true（`menu_demo_spectator_visibility()` 开关，正常游戏不受影响）。
- **司机座位**：改用 `vpart_reference::part().is_seat()` 只选**真座位**（之前用 `BOARDABLE` 会选到后备箱）；被撞出座位后每回合塞回；司机带 `DEBUG_NODMG`。
- **连续公路行驶**：在现实泡泡内（±28 格，步长 3）扫描**最长通畅直段**（`passable` + 无外车 + 无生物），把车摆在段首并朝向该方向；开局即给第一个航点；卡住只补油门不再乱掉头；**不再销毁重建车辆**（那正是"几秒后回到初始状态"的原因）。
  - 实测 `scene_dir_car_run_30`：30 格通畅段，车辆 `42,33 → 46,33 → 47,33 → 48,33 → 49,33 → 51,33`，全程无掉头。

## 16. 2026-11-11 午夜：车辆"转向却仍朝原方向走"的根因与修复

## 19. 2026-11-12 晚：NPC 开火时镜头停滞 —— 相机改为按帧求值

用户反馈：**NPC 开火、子弹在飞的时候镜头就不动了**。

### 19.1 根因

原版两种"动画"会在 `do_turn()` 内部**阻塞**，绕开我们的主循环，所以相机不更新：

| 位置 | 行为 |
| --- | --- |
| `animation.cpp` 的 `basic_animation::progress()` | `draw()` 一次 → 然后 `sleep_for(ANIMATION_DELAY × scale)`，期间只 `pump_events()`，**不再重绘** |
| `animation.cpp` 的 `hit_animation()` | `ui_manager::redraw()` 之后用 `inp_mngr.set_timeout() + get_input_event()` **等输入**（无头进程里就是纯阻塞） |

弹道每推进一步就走一次 `progress()`，于是子弹飞行的那几百毫秒里画面完全静止
→ 看起来就是"开火时镜头卡住"。

### 19.2 改动

1. **相机改成时间的纯函数**（`fp3d_menu_demo_worker.inc`）
   - 相位改成绝对时间：`phase = cam_phase0 + (now - cam_t0) × 0.001 × 0.22`，不再靠 `dt` 累加，
     所以多算几次也不会加速。
   - 封装成 `cam_tick` lambda，注册为 `set_native_menu_frame_hook()`；
     每发布一帧前都会调用它（主循环里也主动调一次，保证 tiles 用的是最新偏移）。
   - 场景结束时 `set_native_menu_frame_hook( nullptr )` 清掉，避免悬空引用。
2. **新增帧钩子**（`fp3d_menu_native_capture.inc` / `sdltiles.h`）
   - `std::function<void()> menu_frame_hook`，在 `menu_record_worker_frame()` 最前面调用。
3. **动画等待改成持续出帧**（`animation.cpp`）
   - `basic_animation::progress()`：演示进程下把 100 ms 的事件泵间隔缩到 16 ms，并且**每次泵完再 `draw()` 一次**。
   - `hit_animation()`：演示进程下不用输入等待，改成 16 ms 一步的
     `pump_events → invalidate → redraw_invalidated → refresh_display` 循环，直到 `ANIMATION_DELAY` 结束。

### 19.4 踩到的坑：PowerShell 改写源码会毁掉非 ASCII

本轮两次把源文件写坏，教训记下来：

- `Get-Content`（Windows PowerShell 5.1 默认按 ANSI 解码）→ `Set-Content -Encoding UTF8` 这种往返，
  会把源码里的 `↓`（lightmap.cpp 注释）和 `…`（animation.cpp 的 `_( "Hang on a bit…" )`）变成乱码，
  后者直接把字符串的收尾引号吃掉 → 编译报 `unterminated argument list invoking macro '_'`。
- 处理办法：`git checkout -- <file>` 还原，然后用 **`edit` 工具**（正确处理 UTF-8）重新施加改动。
- 检查手段：按 UTF-8 解码后搜 `[鈥鈫锛銆]` 这类 GBK 乱码特征，比搜 U+FFFD 有效。

## 20. 2026-11-12 深夜：开车场景"转向却仍按原方向走"的真正根因（打滑）

上一轮我只改了目标点逻辑，并没有修好——这次找到原版机制里的真正原因。

### 20.1 根因：`skidding` 时朝向取转向、位移取旧动量

`map.cpp` 的 `map::move_vehicle()`：

```cpp
if( can_move || ( vertical && veh.is_falling ) ) {
    if( veh.skidding ) {
        veh.face.init( veh.turn_dir );   // 精灵朝向 = 方向盘角度
    } else {
        veh.face = facing;               // 精灵朝向 = 实际行进方向
    }
    veh.move = facing;                   // 位移始终 = 实际行进方向
```

而 `vehicle::move()` 里同样是：打滑时 `mdir = move`（旧动量），不打滑时用 `turn_dir`。
于是**打滑状态下必然会"车头拐过去、车身继续往原来的方向滑"** —— 这正是用户看到的现象。

更关键的是**打滑恢复只挂在玩家身上**：

```cpp
if( player_character.controlling_vehicle &&
    veh_pointer_or_null( veh_at( player_character.pos_bub() ) ) == &veh ) {
    g->calc_driving_offset( &veh );
    if( veh.skidding && can_move ) {
        veh.possibly_recover_from_skid();
    }
}
```

NPC 不是 `player_character`，所以**只要蹭到一次路缘/僵尸，这辆车就会永远处于打滑状态**，
之后整段行驶都是"朝向错、位移对"。

### 20.2 修复

每次世界回合，在开车场景里：

```cpp
if( focus_vehicle->skidding ) {
    focus_vehicle->possibly_recover_from_skid();   // 先走原版恢复
}
if( focus_vehicle->skidding ) {
    focus_vehicle->skidding = false;               // 兜底：演示车不允许长期打滑
    focus_vehicle->face = focus_vehicle->move;     // 朝向对齐真实行进方向
    trace( "..._skid_cleared" );
}
```

同时补了两处配套修正：

- **隐形观察者跟着车走**：相机限幅是相对观察者 ±22 格，车开远后会开出画面；
  现在车离观察者超过 8 格就把观察者挪到车后 3 格（观察者本来就不可见、无敌）。
  相机限幅也改成围绕**观察者当前位置**而不是场景起点。
- 车前清障半径 3 → 6 格，减少被僵尸/杂物堵停。

### 20.3 遥测（新增字段）

`[STAT]` 末尾现在带 `face=<朝向角度> move=<行进角度> skid=<0|1>`：

```

scene=2 kind=2 step=24 veh=67,59,v0   face=75 move=75 skid=0
scene=2 kind=2 step=48 veh=76,123,v0  face=75 move=75 skid=0
```

- 修复前会看到 `face` 与 `move` 不一致、`skid=1`；
- 修复后二者**始终相等**、`skid=0`，trace 里能看到 `scene_2_skid_cleared`（说明确实触发过打滑并被清理）。

## 21. 2026-11-13：车体"斜着/碎裂"的真正原因（15° 转向台阶）+ 难民中心场景

用户截图显示的不是"位移方向不对"，而是**车体本身被画成斜的、甚至碎成两半叠着**。
这一轮把根因定到转向台阶上，并把营地场景换成难民中心。

### 21.1 根因

1. **CDDA 画不了非 90° 的车体**：`vehicle::turn()` 把 `turn_dir` 按
   `vehicles::steer_increment`（15°）累加；`map::move_vehicle()` 里
   `veh.face = facing`，于是车头可以是 15°/30°/75°。
   图集只有 0/90/180/270 四向，斜角时部件被错位绘制 → 截图里的"斜车/碎裂"。
   （遥测里出现 `face=75`、`face=60` 就是这个。）
2. **打滑让朝向与位移分家**：`skidding` 时 `face` 取 `turn_dir`、`move` 取旧动量；
   而打滑恢复只在 `player_character.controlling_vehicle` 时调用，
   NPC 开的车一旦蹭到东西就永久打滑。上一轮已加"清 skidding"，本轮保留。
3. **车道方向可能取成"横穿马路"**：宽路面上东西向也能有 20+ 格连续 road 格。
4. **`TFLAG_ROAD` 也包含土路/碎石路**：上一轮车就开进了林间土路。

### 21.2 改动

- **每回合把车头吸附到 90° 轴**：
  ```cpp
  const int deg_snap = ( ( ( deg_now % 360 ) + 45 ) / 90 ) * 90 % 360;
  if( focus_vehicle->move.dir() != snapped ) {
      focus_vehicle->move.init( snapped );
      focus_vehicle->face.init( snapped );
  }
  focus_vehicle->turn_dir = focus_vehicle->face.dir();
  focus_vehicle->last_turn = 0_degrees;
  ```
  trace 记 `scene_N_axis_snap_<角度>`。
- **车道轴向按铺装延伸判定**：从落点向四个方向各探 60 格 `t_pavement*`/`t_sidewalk*`，
  取最长的那个轴（trace `scene_lane_axis_x_x.._y..`），只在**该轴**上找走廊。
- **只认铺装路面**：`is_paved()` = 地形 id 前缀 `t_pavement` 或 `t_sidewalk`，
  不再用 `TFLAG_ROAD`（土路/碎石路也会有这个 flag）。
- **降速跑满一段**：cruise 400、每回合补到 300（原 600/480），走廊 20–28 格，
  整段约 10 秒，正好填满 12 秒的场景，不会开到地图边缘。
- **视线跟着车**：车离隐形观察者超过 8 格就把观察者挪到车后，相机限幅围绕观察者当前位置。

## 22. 2026-11-13 晚：镜头抽搐、车开几秒就停

### 22.1 镜头抽搐：裁剪用的是"下一帧"的 pan

`menu_record_worker_frame()` 开头会调用帧钩子推进相机，然后才裁剪当前帧。
但相机的小数平移（`menu_canvas_pan_x/y`）**同一个变量**既给钩子更新、又给裁剪使用，
于是"画面是按旧整数格画的、裁剪却按新小数格平移"，
一旦这中间跨过一格（pan 从 +0.99 翻到 -0.01 且整数 +1），裁剪就整格跳一次 —— 就是抽搐。

修法：新增 `set_native_menu_capture_pan()`，worker 在 `cam_tick()` 之后、`redraw()` 之前
把当时的 pan **快照**下来，裁剪只读快照；钩子继续推进 live 值，只影响下一帧。

实测（连续 25 帧的像素位移）：`12,13,10,8,10,1,10,10,9,7,9,7,7,7,5,5,6,4,1,4,3,9,2,2`
—— 最大 13px，**没有出现 32px（一格）的跳变**。

### 22.2 车开几秒就停：三个独立原因叠在一起

1. **航点是死目标**：`car_wp_b` 固定在起点前方 20–26 格，`drive_to_local_target()` 一到就收油。
   → 改成**滚动航点**：每回合把航点设成"车当前 + 车道方向 × 12 格"，永远够不着，所以一直开。
2. **车体后半截被别车顶住**：清障循环只从 `i = 0`（轴心）向前清，
   而 2×4 的车体向轴心**后方**也伸出一格 → 后面的停放车辆把车卡死（表现为
   `veh=…,v283` 有速度却坐标不动）。→ 清障范围扩到 `i = -2 … run + 2`。
3. **开到地图边缘**：滚动航点会一路把车推到 x=128（132 地图边界）才停，
   那里路面已经没有了。→ 滚动航点限制在起点 30 格内，超出就保持最后航点自然收油。

另外加了**保险**：车连续 8 回合速度为 0（真的被墙/残骸卡死）就 `scene_done`，
直接切下一场，不再让观众盯着停住的车 10 秒。

## 24. 2026-11-14：菜单子界面里背景继续播放，进入游戏才停

用户要求：进设置等界面时背景会暂停，取消这个；改成一直播放，直到玩家真正进入游戏才停。

### 24.1 原因

`main_menu.cpp` 在 `CONFIRM` 分支里对子界面（设置 / 世界 / 建角色 / 帮助）做了：

```cpp
set_main_menu_demo_active( false );
on_out_of_scope restore_title_backdrop( []() { set_main_menu_demo_active( true ); } );
```

`main_menu_demo_active` 是**唯一的**背景开关：`refresh_display()` 里

```cpp
if( main_menu_demo_active ) {
    menu_demo_draw_live_frame( width, height, SDL_GetTicks() );
}
```

所以关掉它就等于"整段时间不再取帧、不再绘制背景"——在能看到背景的界面上表现为**冻结**，
回来时又是一张"跳过去"的画面。

### 24.2 改动

1. **不再为子界面关背景**（`main_menu.cpp`）：删掉那对 `set_main_menu_demo_active(false/true)`，
   注释改为说明"这些界面虽然是不透明的、会盖住背景，但演示必须继续跑"。
   背景只在 `opening_screen()` 返回（= 玩家真的开局/读档进游戏）时停止，
   那里原有的 `on_out_of_scope` 仍会 `set_main_menu_demo_active(false); stop_native_menu_demo();`。
2. **看门狗不再误杀**（`fp3d_menu_native_capture.inc`）：
   原来 `menu_last_progress` 只在**父进程取帧**时刷新；一旦某段时间不绘制背景，
   20 秒后看门狗把健康的 worker 杀掉重启（画面直接回到第一场）。
   新增轻量探测 `menu_shm_peek_seq()`：看门狗直接读共享内存的序号，
   只要序号在推进就刷新 `menu_last_progress`，从而"没在画但还在出帧"不再算卡死。
